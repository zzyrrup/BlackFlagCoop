## Final answers

1. **Where are composition schemas loaded?**  
   They are **stored** in `.edata` as embedded JSON-like catalogs. The **runtime loader/parser function is not identified**.

2. **Where is `player.position` registered?**  
   **Statically** at composition `0xA1D77B5` and STANDARD event `0xA1DE0FE`. Runtime registration API **not found**.

3. **How are telemetry events constructed and dispatched?**  
   **Unknown offline.** Schema shape is known; builder/dispatch/serialization RVAs are not.

4. **Where do XYZ float values originate?**  
   **Unknown.** Declared as floats; no producer traced to gameplay position.

5. **Verified connection to Edward’s actor or transform?**  
   **No.**

6. **Safe, documented path toward reading player position?**  
   **Not yet.** No supported read API, sink, or verified producer. Placeholder BFC coords remain unverified.  
   Honest path: continue offline producer/sink identification → only then design a **read-only** observation experiment under explicit approval.

7. **Next best milestone?**  
   **v0.5.10 — schema-blob consumer hunt:** find code that references the STANDARD/CUSTOM event table structure (length/count headers, rip-relative loads of `.edata` blob base, or string compares against `"type\":\"STANDARD\"` immediates), without assuming Harbour. Secondary: map `OnlineLiveTelemetryRuntimeConfig` / metric-export jobs only as a **sink** lead, still not a pose reader.
