## Discovered

### Confirmed — no direct `Allocator(0x20F0)` / absolute size-field reader

| Probe | Result |
|-------|--------|
| RIP refs to size field `0xB2898E8` | **0** readers (InstallerA is the writer of size+ctor) |
| RIP refs to ctor field `0xB289918` | **2** (InstallerA store only; duplicate decode) |
| `mov r32, 0x20F0` then `E8 Allocator` | **0** across all code sections |
| Imm `0x20F0` sites | **12** — mostly **field offsets** (`[obj+0x20F0]`) or the TypeInfo registration write |

Notable false lead: `0x3670EF0` has `imm 0x20F0` **and** calls Allocator, but allocates **`0x4250`** bytes; `0x20F0` is used as **`mov [obj+0x20F0], …`** (field), not the heap size.

**Confirmed:** construction of the `0x59D9660` composite does **not** use a hard-coded `Allocator(0x20F0)` immediate. Size remains TypeInfo-registered at **`0xB2898E8`**, consumed (if at all) via a **generic Lookup→TypeInfo** path rather than absolute RIP to this record.

**Hypothesis (not verified):** a shared factory does `ti=Lookup(key); size=*(u32*)(ti+0x20); ctor=*(fn*)(ti+0x50); Allocator(size); ctor(obj)`. Multiple Lookup sites touch `+0x20`/`+0x50`, but none were uniquely proven as this record’s factory in the sampled windows.

### Confirmed — helper `0x546D150` (491 B)

| Item | Value |
|------|-------|
| E8 callers | **40** (shared) |
| Fast path | If `[obj+0x98]==0`: search nested via `[obj+0xA0]` packed lists; return matched entry pointer |
| Side-block path | If `+0x98` present: mode at `[block+0x48]` (`1`/`2`); resolve through TLS bitmasks / `+0x176` / `+0x138` tables |
| Return | Source pointer used by neighbor to **`vmovups`** into `obj+0x40…` |
| Alloc/Lookup/Outer | **No** |

### Confirmed — edx=3 arm-table callee

| Item | Value |
|------|-------|
| Neighbor | `0x2335140`: `test edx,~2` → **`mov edx,3; call [vt+0x2B0]`** |
| Arm table `+0x2B0` | **`0x4656C80`** trampoline → `[vt+0x2B8]` |
| Arm table `+0x2B8` | **`0x2108620`** wrap (same as edx=2 arming chain) |

**Confirmed:** edx=3 does **not** select a different `+0x2B0` slot; it reuses the same trampoline→wrap path as edx=2. edx is preserved into the wrap/canonical callees; wrap body does not branch on edx for mode selection (modes still come from side-block `+0x158` / listHelper args).
