## Workstream A — Candidate `0x57AF060`

### Boundaries (medium confidence)

| | |
|--|--|
| Entry RVA | `0x57AF060` |
| Entry file | `0x57AE660` |
| End RVA | `0x57B0564` |
| Size | **5380** bytes (`0x1504`) |
| Section | `.impdata` |
| Method | INT3 run after body |
| Prologue | `push rsi/rdi/rbx; sub rsp,0x30; mov rsi,rcx;` + AVX zero |

### Callers / callees

- **Direct E8 caller:** `0x57A9ED7` (nearby — same subsystem neighborhood; **startup phase not statically proven**)  
- **Notable callees:** `0x53519E0` (string helper), `0x1A64E70` (follow-on), `0x4868810` (early), plus many others  
- **LEA count:** 94 (≈92 into schema JSON-like `.edata` text)  
- **`0x4DB` imm count:** 6 (multiple chunk lengths, not a one-off)

### High-signal site `0x57AF8D9` (confirmed)

Linear behavior:

1. Local SSO/string bookkeeping (`cmp rax, 0x10`, size field at `[rsi+0x10]`)  
2. `lea rdx, [0xA1DEAFE]` → embedded `{"name":"player.position",...}`  
3. `mov r8d, 0x4DB`  
4. `call 0x53519E0`  
5. Continues with **another** chunk (`0x47A` length + another schema LEA + same helper)

### What the function appears to do (evidence-based)

It is a **hardcoded enumerator of many embedded telemetry schema text slices** (attribute dictionary fragments, STANDARD/CUSTOM/CONTEXT events, composition/signal maps). For each slice it materializes a **pointer+length** into a string-like object via `0x53519E0`, and also invokes `0x1A64E70`.

It is **not** a single-block special case for `player.position` only — `player.position` is one of many chunks.

## Final answers

1. **What does `0x57AF060` do?**  
   Offline: initializes/consumes **many hardcoded telemetry schema text chunks** from `.edata` (including a `player.position` multi-event window), building string objects and calling follow-on helpers. Exact product type (full registry vs temporary strings) unproven.

2. **What does `0x53519E0` do?**  
   Widely used **pointer+length → string (SSO) materializer**. Not a schema parser.

3. **What does `0x1A64E70` do?**  
   Small, hot follow-on called from the candidate (and many other sites). **Semantics not fully established**; not proven as parser/registry.

4. **Is the `0x4DB` block parsed or merely passed/copied?**  
   **Passed/copied** into a string-like object (confirmed pattern). **Parse not confirmed.**

5. **Are runtime descriptors created?**  
   **Not confirmed.**

6. **Connection to live player position?**  
   **No** — only to schema **definition text**.

7. **Connection to Edward’s actor?**  
   **No.**

8. **Next best path toward a second independently controlled Edward?**  
   This telemetry-schema init path is **orthogonal** to dual-Edward control.  
   - Short-term: decode what `0x1A64E70` stores (globals/vtable) after string assign — still offline.  
   - Dual-Edward: resume **actor factory / possession / input ownership** research; do not wait on telemetry floats.

## Confirmed vs hypotheses

**Confirmed**

- Function extent ~`0x57AF060`–`0x57B0564`  
- Exact LEA to `player.position` + `0x4DB` + call `0x53519E0`  
- Dozens of other schema-text LEAs in the same function  
- `0x53519E0` SSO string helper behavior  

**Hypotheses**

- Candidate runs during telemetry subsystem init  
- Strings feed a later registry/parser via `0x1A64E70`  

**Unresolved**

- Descriptor tables, live event emission, XYZ producers, Edward/actor links
