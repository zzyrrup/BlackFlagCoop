# BlackFlagCoop v0.8.0 — Second Edward proof-of-life

**Date:** 2026-11-12  
**Target:** Assassin's Creed Black Flag Resynced 1.0.6  
**Installed ASI:** v0.5.1 `63B38877DDA7CC7CD9AB2619F94D3941C37F54C95A435EFE47084DC4CF2A50BE` (not replaced)  
**Mode:** offline PE plus a default-off plugin gate. No launch, no deploy, no live memory, no PC2.

## Decision

The native character factory is **not confirmed**, so this build does **not** call the game.

The strongest evidence-backed route is the reflected **spawn-parameter** family, not the deferred actor queue. Those parameter functions serialize and copy a params object. The missing link is the callsite that fills `SpawnNPCParams` or `SpawnCharacterParams` and then creates a world entity.

| Question | Result |
|----------|--------|
| Native spawn path confirmed | **No.** Types and serializers are confirmed. The create/apply callsite is not. |
| Second actor instantiated | **No.** Not in this build, and not in-game tested. |
| Independent Player 2 input / possession | **No.** Not implemented. |
| What this build does | Logs a refusal. Creates nothing. Leaves Player 1's Edward untouched. |

## Why the old queue path is not the factory

v0.6.5 through v0.6.25 followed `CreateActorsDeferredSingleThreaded` (`0x1AC380`), LOD enqueue, and owner vtable constructors. That chain updates objects that already exist. It has no Edward, archetype, or character-construction edge. Those RVAs stay out of the callable set.

## Confirmed parameter types

Each name has one RIP `lea` inside a registrar. The registrar writes the type name and hash through `0x4572C60`, then calls its parent registrar. Direct `E8` callers of the player, NPC, first-person, and boat registrars: **none**. `SpawnCharacterParams` is called only by those derived registrars.

Inheritance, from the parent call:

`SpawnPlayerParams`, `SpawnFirstPersonPlayerParams`, `SpawnNPCParams`, `SpawnPlayerBoatParams`  
→ `SpawnCharacterParams` (`0x80F2330`, hash `0xFB7FF6A5`)  
→ `SpawnEntityBuilderParams` (`0x8E02960`, hash `0x6A484E77`)  
→ `SpawnEntityParams` (`0x8DFFB90`, hash `0xB5BAEE39`)

`SpawnInventoryParams` joins at `SpawnEntityBuilderParams`.

| Type | Registrar | Hash | Descriptor (record base) |
|------|-----------|------|--------------------------|
| SpawnEntityParams | `0x8DFFB90` | `0xB5BAEE39` | `0x92D2068` |
| SpawnEntityBuilderParams | `0x8E02960` | `0x6A484E77` | `0x92D1EE8` and `0x92D1FA8` |
| SpawnCharacterParams | `0x80F2330` | `0xFB7FF6A5` | `0x92D19C8` |
| SpawnNPCParams | `0x80F23E0` | `0x94D05600` | `0x92D1AA8` |

Registrar shape, confirmed from the disassembly: `rcx` is the object being described, `rdx` is a serialization context. It stores `[rdx+0x38]=rcx`, publishes the name/hash, saves and restores `[rdx+0x40]`, calls the parent, then `0x4987180`.

## Descriptor record (stride `0x20`)

Each registrar's absolute pointer appears once in `.edata` (the builder appears twice). The repeating slot at record+0 is `0x53741F0`, which is a single `ret`.

| Slot | SpawnNPCParams | SpawnPlayerParams | Role from the body |
|------|----------------|-------------------|--------------------|
| +0x00 | `0x53741F0` | `0x53741F0` | empty `ret` |
| +0x08 | `0x80F23E0` | `0x80F2A20` | name/hash registrar |
| +0x10 | `0x12071F0` → `0x1207200` | `0x64099B0` → `0x1207200` | field visitor, same offsets the registrar names (`+0x58`, `+0xA8`) |
| +0x18 | `0x5E3DB0` | `0x21F5950` | params copy: `0x43DCB00` then a field copy |

`0x1207200` and `0x5E3DB0` / `0x21F5950` are not world-spawn functions. `0x43DCB00` returns a destination pointer inside the copy helper. That is not evidence it creates Edward.

A static initializer stores character hash `0xFB7FF6A5` beside boat hash `0x3DF9C374` and the dword `0xB8` (`0x645BA72`). The dword's meaning is **not** confirmed. It is not used as an allocation size in this milestone.

## Candidate for a second Edward

`SpawnNPCParams` is the candidate type for a second body. `SpawnPlayerParams` and `SpawnFirstPersonPlayerParams` describe the existing player. Reusing them is the wrong first call even after a factory is found, because that path can belong to Player 1.

Edward's archetype id, the transform argument, and the world/entity receiver are **unknown**.

## What the plugin does

`BFC_SECOND_EDWARD=1` (also `on` / `true`) asks for the proof-of-life. The gate defaults off. Either way `EvaluateSecondEdward` returns `actorCreated=false` and does not call an RVA. The log line says `REFUSED` when the gate is on, and names the missing link.

## Submission trace

`docs/v0.8.0-submit-path.md` is the evidence table. The NPC and player copy helpers have no direct callers. Both hashes occur in the registrar and once each in `.edata`. The helpers clone a params object. They do not submit it. AC4Coop's `EntityBuilder` symbol names are absent from this exe. The gate stays refused.

## Next concrete step

Resolve the virtual calls at `0x33593D0` (`+0xC0`) and `0x335A228` (`+0x20`) inside `0x33591C0`. That function is the only non-initializer that passes NPC type global `0xB5378F0` into `0x137AE80`. If those calls only touch the reflection node, leave this params family.
