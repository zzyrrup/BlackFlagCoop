### What this establishes

1. This build exports a **partially real** Harbour StringId registry surface: Find / DumpTo / LoadFrom / ClearUnsafe look executable; Insert and GetIdentifier\* are stubs.  
2. Stub Insert/GetIdentifier implies either dead export stubs, alternate internal entry points, or stripped residual symbols — **not** a confirmed public API for inserting telemetry names at runtime from a plugin.  
3. **Telemetry binding remains unproven.** No caller graph from schema JSON → Registry_Find → PlayerPos\* producer was established offline.

## Schema parser conclusions

1. Prefer **blob/schema parse** over relocated C-string pointer tables (v0.5.6 absolute-VA xref scans still negative for `PlayerPos*` dictionary sites).  
2. Harbour `Registry_Find` / `DumpTo` / `LoadFrom` are the best **offline** reverse-engineering targets for understanding StringId storage — but they are **not** yet shown to touch player telemetry.  
3. `DumpTo`/`LoadFrom` suggest registry persistence or tooling paths; useful for future static analysis of format, not for overnight ASI hooks.

## Explicit non-claims

- No verified schema parser function RVA for telemetry JSON.  
- No verified event construction / dispatch routine.  
- No legitimate Edward world-coordinate observation path for the ASI.  
- Working game ASI remains **v0.5.1**.
