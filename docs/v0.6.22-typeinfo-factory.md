## Discovered

### Confirmed — generic TypeInfo factory idiom (tight)

Across code that calls Lookup (`0x429F9E0`) then Allocator (`0x426EE50`), five functions **tight-verify** the hypothesized idiom:

| Step | Instruction pattern |
|------|---------------------|
| 1 | Obtain TypeInfo (`Lookup` and/or prior vcall returning ti) |
| 2 | `mov r*d, [ti+0x20]` — **dword size** (matches registered `0xB2898E8`) |
| 3 | `movzx …, byte [ti+0xF6]; and …, 0x7F` — flags/align into r8d |
| 4 | `mov edx, <sizeReg>; call Allocator` |
| 5 | `call qword ptr [ti+0x50]` — ctor icall (matches registered `0xB289918`) |

**Tight hits (not LookupKey-tied):**

| Func | E8 xrefs (capped) | Notes |
|------|-------------------|-------|
| `0x238590` | **80** | Canonical example; Lookup then size/alloc/ctor |
| `0x256280` | **61** | Same idiom; Lookup early |
| `0x218900` | 2 | Clone |
| `0x218660` | 0 (likely LEA/indirect) | Clone |
| `0x21FA70` | 0 (likely LEA/indirect) | Clone |

**Confirmed:** construction of TypeInfo-registered objects (including size `0x20F0` when that TypeInfo is supplied) uses this **generic** factory path, not a hard-coded `Allocator(0x20F0)`.

**Confirmed:** **no** tight factory is RIP-tied to LookupKey `0xB2898C8`. Key-LEA funcs (33) show Lookup/partial edges only; loose “full” hit `0x2F2C1A0` (key=true) **fails** tight verify (unrelated Alloc / no `[ti+0x50]` ctor).

Loose co-occurrence scan: 48 candidates, 16 “full” (Lookup + +0x20 + Alloc + icall) — many false positives from `[reg+0x20]` as flags/pointers. Tight verify reduces to **5**.
