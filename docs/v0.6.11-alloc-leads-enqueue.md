## Discovered

### Confirmed — `0x400B50` (447 bytes)

| Item | Value |
|------|-------|
| Nested / lookup / allocator | **yes / yes / yes** |
| Direct enqueue/wrapper | **no** |
| Alloc site | `0x400C39` → `0x426EE50` with **`edx = 0x50`** |
| Coordinator path | `[rcx+0x38] → [+0x58] → [+0xA8] → [+0x3CD0]` then lookup `0x429F9E0`, then `[result+0x18]` |
| Other | reads `[…+0x98]`; LEA vtable installs `0xB46A060`, `0x93DD990`; `0x1C8` used as **offset add**, not proven alloc size |
| Callers (E8) | `0x2971ED0`, `0x485CC20`, `0x6F19CF0` — nested+lookup, **no** enqueue |

### Confirmed — `0x4444C0` (1914 bytes)

| Item | Value |
|------|-------|
| Nested / lookup / allocator | **yes / yes / yes** (lookup×2, allocator×2) |
| Direct enqueue/wrapper | **no** |
| Alloc site | `0x444641` → `0x426EE50` with **`edx = 0xE0`** (also other allocator call) |
| Coordinator path | same `[rcx+0x38]→[+0x58]→[+0xA8]→[+0x3CD0]` pattern |
| Init stores | writes **`[obj+0x18]`**, **`[obj+0x98]`**, **`[obj+0xA8]`** (object-field init) |
| Callers (E8) | `0xCD76C84`, `0xD720692`, `0xD7225A3` — **no** lookup/enqueue in analyzed windows |

### Confirmed — enrollment

| Probe | Result |
|-------|--------|
| Lead → enqueue helper/wrapper (direct) | **false** |
| Lead forward-reach queue within depth 3 | **false** for both |
| Caller/hop2 → enqueue or wrapper | **0** of 12 edges |
| Caller → lookup (for `0x400B50` callers) | **3** edges (share coordinator lookup, not enqueue) |

**Verdict:** These leads sit on the **shared coordinator lookup + allocator** periphery and (for `0x4444C0`) initialize fields overlapping the subject fingerprint offsets, but they are **not** shown to enroll objects into the deferred queue / wrapper `0x2E97FC0`.

**Hypothesis (not verified):** They may allocate related helper/descriptor objects (`0x50` / `0xE0`) attached to a manager that also owns the `+0x3CD0` coordinator — distinct from the queued LOD subject.
