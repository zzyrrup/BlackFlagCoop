# BlackFlagCoop v0.6.5 — Deferred queue worker and 16-byte element

**Date:** 2026-11-12  
**Target:** AC Black Flag Resynced 1.0.6  
**Mode:** Offline PE only  
**ASI:** v0.5.1 preserved (`63B38877…`); not opened or replaced  
**EXE SHA256:** `19920F34BB2FAC814023EE3C27F0CECA1872E80A2AAFB37C092C419FFF77CC0D`  
**Image base:** `0x140000000`  
**Tool:** `tools/offline/QueueWorker065` (Iced 1.21 linear disassembly)

## Executive verdict

The deferred array at `[coordinator+0xAC0]` is a list of **existing object pointers plus a scalar score**. Each 16-byte slot holds a pointer at `+0`. `0x1AC380` writes a computed float at `+8`, then calls `0x725400(object, 1)` and `0xE95E80(object)` with that pointer.

`0x725400` is a **shared flag and hashed-list helper** on the object. `0xE95E80` is **called only from this handler**. It allocates a **0x160-byte side block**, links that block to the object that was already in the queue, and walks pointer arrays on that object. Neither function receives the 16-byte slot address. Neither function shows an Edward, character, archetype, player, or transform construction path.

The queue is **not** a generic callback list, and it is **not** shown to carry actor-creation requests. It drains already-queued objects.

## 16-byte element layout

Stride is 16. `r12` advances by `0x10` in the per-object loop, and the score loop does `add rbx, 0x10`.

| Offset | Size | Classification | Confidence |
|--------|------|----------------|------------|
| `+0x00` | 8 | Pointer to an existing object. Loaded and passed in `rcx` to both workers. Also dereferenced as `[ptr+0x18]` then a 16-byte vector at `+0x50`. | **High** |
| `+0x08` | 4 | `float` score **written by the handler**, later compared with `25.0`. | **High** that it is an `f32` result. **Medium** that the math is a squared distance. |
| `+0x0C` | 4 | Not read or written by `0x1AC380`, `0x725400`, or `0xE95E80`. The tail copy can move these bytes. No evidence they are padding, an id, or a flag. | **High** that these three functions do not interpret them. |

### How `+0` is passed

```text
0x1AC4C3  mov rax, [rsi+0xAC0]     ; array base
0x1AC4CA  mov r14, [rax+r12]       ; qword at element + 0; r12 steps by 0x10
0x1AC4CE  mov rcx, r14
0x1AC4D1  mov dl, 1
0x1AC4D3  call 0x725400
0x1AC4D8  mov rcx, r14
0x1AC4DB  call 0xE95E80
0x1AC4E3  add r12, 0x10
```

The same pointer load is repeated at `0x1AC512` (`mov r14, [rax+rcx]`) for the threshold loop, then the same two calls at `0x1AC51B` and `0x1AC523`.

### How `+8` is produced

```text
0x1AC451  vmovaps xmm6, [rcx+0x110]          ; reference vector
0x1AC460  mov rax, [rbx]                     ; element + 0
0x1AC463  mov rax, [rax+0x18]
0x1AC467  vmovaps xmm8, [rax+0x50]           ; 16-byte vector
0x1AC46C  call 0xD530                        ; returns an XMM mask
0x1AC471  vblendvps xmm0, xmm8, xmm7, xmm0   ; blend toward zero
0x1AC477  vsubps xmm0, xmm0, xmm6
0x1AC47B  vmulps xmm0, xmm0, xmm0
0x1AC47F  vhaddps xmm0, xmm0, xmm0
0x1AC483  vmovss dword ptr [rbx+8], xmm0
0x1AC488  add rbx, 0x10
```

`0xD530` is a 22-byte thunk: `lea rcx, [0x97B7430]; call 0x421A990`. Its data pointer is not a string. The constant compared later is the `f32` at `0x97C5C00`, which is **25.0** (`00 00 C8 41`):

```text
0x1AC4F1  vmovss xmm6, dword ptr [0x97C5C00]
0x1AC507  vucomiss xmm6, dword ptr [rax+rcx+8]
0x1AC50D  jb 0x1AC540                        ; stop the extra pass when score > 25
```

`vucomiss` / `jb` continues the extra pass while `25.0` is not below the stored score. The subtract-multiply-horizontal-add sequence is the arithmetic of a sum of squared component differences of two 4-wide vectors. That supports reading `+8` as a score. It does not identify the vectors as a world transform, and it does not write a transform.

After the processed prefix, the handler byte-copies the tail back to the array base through `0x53519E0(base, tail, byteCount)` and stores the remaining count in the low 14 bits of `[coordinator+0xAC8]`, preserving the high bits with `0xFFFFC000`.

## Worker `0x725400`

| Field | Value |
|-------|--------|
| Entry | `0x725400` |
| Exclusive end | `0x725649` |
| Size | **585** bytes |
| Section | `.impdata` |
| Frame | `sub rsp, 0x38` |
| `rcx` | Object pointer from element `+0` |
| `dl` | `1` from both handler sites |

### What the queue path does (confirmed)

`rsi` keeps the object pointer.

- Loads the byte at **object `+0x61`**.
- If bit 2 (`0x04`) is set and `dl == 0`, it takes the other path at `0x7255CE`. The handler passes `dl = 1`, so that branch is not the queue path.
- If bit 2 is set, it clears bit 2 and stores the byte back.
- If bit 3 (`0x08`) is set, it follows `+0x18 → +0xA8 → +0x3CD0`, passes the opaque bytes at `0xB2898C8` to `0x429F9E0`, then searches a list for this object pointer. Records are **0x18** bytes apart (`add r14, 0x18`, `cmp [r14], rsi`). A hit compacts the list with `vmovups` of 16 bytes plus a trailing qword and calls `0x4C9CF60`.
- On the way out it clears bit 1 (`and al, 0xFD`) and stores `+0x61` again.

`0x725650`, called from the removal path as `(container, object)`, starts with a pointer hash (`shl 0x15`, `not`, `shr 0x18`, `imul 0x109`). Its strings are the allocator-failure and "Too many elements for %sArray" messages. Role: **hashed collection maintenance for this object pointer**. It is not an allocator of a new character.

### Other callers

Direct `E8` sites whose displacement lands on `0x725400`:

| Site | Boundary | Setup |
|------|----------|--------|
| `0x1AC4D3` | Instruction boundary inside `0x1AC380` | `rcx = object`, `dl = 1` |
| `0x1AC51B` | Same function | `rcx = object`, `dl = 1` |
| `0x4B5A661` | Real call | `mov rcx, rsi; xor edx, edx` |
| `0x4D04D7C` | Real call | `mov rcx, rsi; xor edx, edx` |
| `0x129E51D8` | Real call in `.code` (`48 89 F1 31 D2 E8`) | `mov rcx, rsi; xor edx, edx` |

No `LEA` and no absolute qword in the image points at `0x725400`. The helper is shared. The `dl = 0` callers are outside this queue and were not followed further.

The bytes at `0xB2898C8` are not text (`A2 C3 FF FF FF FF 06 C4 …`). They stay an opaque key.

## Worker `0xE95E80`

| Field | Value |
|-------|--------|
| Entry | `0xE95E80` |
| Exclusive end | `0xE96BA4` |
| Size | **3364** bytes |
| Section | `.impdata` |
| Frame | `sub rsp, 0x398` |
| `rcx` | Same object pointer, saved in `rsi` |
| Callers | **Only** `0x1AC4DB` and `0x1AC523` |

No `LEA` and no absolute qword points at the entry.

### Side allocation (confirmed)

When the global qword at `0xAF6FD48` is usable, the function calls `0x426EE50(context, 0x160, 8)`. The file image of that global is zero; the pointer is runtime state. If the allocator returns null, the fallback is a virtual call `[vtable+0x40]` with `edx = 0x160`, `r8d = 8`.

The 0x160 block is then filled with Anvil-style small-array headers (low 14 bits count, `0xFFFFC000` mask, `0x80000000` flag, inline begin pointers such as `[block] = block+0x10`). Two stored qwords are **function pointers**, not MSVC vtables:

| Stored at | Target | Body |
|-----------|--------|------|
| block `+0x50` | `0x7B04200` | 42-byte function. Calls `0x4B4EB70` on `rcx+8`, optionally `0x43F8CB0`, returns the object. |
| block `+0x130` | `0x2E9FA60` | 11-byte predicate: `mov rax, [rcx+8]; cmp dword [rax], 0; sete al`. |

No MSVC RTTI name was recovered for either target (`signature == 1` and `pSelf` check failed).

The block is linked to the queued object:

```text
0xE9607C  mov [rsi+0x98], rbx      ; object->side = block
0xE96083  mov [rbx+0x100], rsi     ; block->object = object
0xE9608A  mov rax, [rsi+0x18]
0xE9608E  mov [rbx+0xF8], rax      ; copy object+0x18
```

`0x160` bytes of small-array headers plus a back-pointer is a side context attached to an object that already existed in the queue.

### Other confirmed object fields used by this function

These offsets are on the **object**, not on the 16-byte slot.

| Offset | Use |
|--------|-----|
| `+0x00` | Vtable. Tail path can `call [rax+0x230]`. |
| `+0x18` | Copied into the side block at `+0xF8`. |
| `+0x22`, `+0x23` bit 2, `+0x25` | Byte tests gating a later side-block update. |
| `+0x28` / `+0x30` | Pointer array and count (`shl 3` / mask `0x1FFF8`). |
| `+0x34` / `+0x3C` | Second pointer array and count. |
| `+0x40` / `+0x48` | Pointer array grown by `0x44FC200` (element size 8, count mask `0x3FFF`). |
| `+0x68` | Address passed to `0xB27210` with the side block. |
| `+0x98` | Receives the new 0x160 block. |

`0xB27210` then operates on that `+0x68` structure: `lock cmpxchg` at `+4`, dword stores at `+8` and `+0xC`, byte at `+0`. That is a list/refcount header on the object. It is not the queue slot.

Pointer-array walks virtual-call entries (`[vtable+0x20]`, `[vtable+0x68]`, `[vtable+0x48]`, `[vtable+0x50]`). One filter compares words at `[desc+0x4C]` and `[desc+0x4E]` with the constants **65535** and **36084** at `0xB2888BC` / `0xB2888BE`. Those are global descriptor limits, not a per-entity id loaded from the queue slot.

`0x7B02D70` (71 bytes) is called with an array entry and the side block. It copies a word, stores the side pointer at `+0x38`, sets a flag bit, and tail-jumps through `[vtable+0x50]`. Its address is near `0x7B00B60` and that proximity is not a call edge. The body is a stamp-and-dispatch, not `UpdateActorControllersSingleThreaded`.

Strings recovered inside `0xE95E80` are only:

- `Invalid pointer not allocated by our allocators or already freed: 0x%p`
- `Too many elements for %sArray. Size: %u, Max Size: %u`
- `Small`

No Edward, character, archetype, player, entity, transform, spawn, or component name appears in either worker.
