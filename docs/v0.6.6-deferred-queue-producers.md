## Investigated

- Who **stores** object pointers into the deferred array at coordinator `+0xAC0` / count `+0xAC8`.
- Displacement scan for `+0xAC0`/`+0xAC8` across `.impdata`/`.code`, then iced verify.
- High-signal filter: same `0x3FFF` / `0xFFFFC000` / stride-`0x10` packing used by consumer `0x1AC380`.

## Discovered

### Confirmed — enqueue helper `0x2E97B60`

| Field | Value |
|-------|-------|
| Entry | `0x2E97B60` |
| End | `0x2E97D18` (INT3) |
| Size | **440** bytes |
| Args | `rcx` = coordinator; `rdx` = object pointer to enqueue |
| Lock | `lea rsi,[rcx+0x1A0]; call 0x42256B0` then unlock via `jmp [lock]` |

Enqueue sequence (capacity available path):

1. `count = [coord+0xAC8] & 0x3FFF`; capacity = `([coord+0xAC8] >> 16) & 0x3FFF`.
2. `newCount = count + 1`; write back with high bits preserved (`and 0xFFFFC000 | newCount`).
3. `base = [coord+0xAC0]`; `shl index,4`.
4. **`mov [base + index - 0x10], object`** — slot `+0` pointer.
5. **`mov dword [base + index - 8], 0`** — clears score float at slot `+8` (matches v0.6.5 layout).
6. On overflow: Small-array grow (`0x42EB100` / `0x4265F00`) with the same `"Too many elements…"` / `"Small"` asserts as the consumer.

This is the **producer** of the queue that `0x1AC380` drains. It does **not** construct the object; it only appends an existing pointer.

### Confirmed — sole callers live in `0x2E97FC0`

| Site | Setup | After call |
|------|-------|------------|
| `0x2E98AA3` | lookup → `add rcx,0x20`; `rdx=rbx` | `or byte [rbx+0x61], 4` |
| `0x2E9B3D1` | same | `or byte [rbx+0x61], 4` |
| `0x2E9B481` | same; object in `r14` | `or byte [r14+0x61], 4` |

- **3** direct `E8` callers of `0x2E97B60`; **all** inside wrapper `0x2E97FC0` (~22KB, frame `sub rsp,0x678`).
- Wrapper early gate: `[rcx+0x180]` non-null, then vector path via `[+0x1818]` (same neighborhood as deferred score math in v0.6.5).
- Coordinator for enqueue is obtained through object nested chain `+0x18 → +0xA8 → +0x3CD0`, then `0x429F9E0`, then **`+0x20`**.
- **No** direct `E8` callers of `0x2E97FC0` found → likely phase / function-pointer dispatch (same pattern as `0x1AC380`).

### Confirmed — flag lifecycle link to worker `0x725400`

| Stage | `object+0x61` bit 2 (`0x04`) |
|-------|-------------------------------|
| After enqueue (`0x2E97FC0`) | **Set** (`or …, 4`) |
| In deferred worker `0x725400` (v0.6.5) | **Cleared** when processing with `dl=1` |

This closes a consume/produce loop on the same flag byte documented in v0.6.5.

Raw scan: 1168 verified hits; 179 stores. Most are unrelated object layouts, stack slots `[rsp+0xAC0]`, or false `adc`/`sub` decodes. Only `0x2E97B60` matched the deferred packing invariants.
