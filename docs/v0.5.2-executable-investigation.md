## 6. Conclusions

### Best evidence-backed leads for Edward’s actor

1. **Composition / schema path:** expand the JSON blob around `PlayerPosition` → `player.position` and related entity schema fields (`*EntityId`). This is the strongest offline lead for a data-driven Anvil component naming scheme.
2. **Update-phase labels:** `CreateActorsDeferredSingleThreaded` and nearby single-threaded update names as **research beacons** (not hooks yet).
3. **Ally world-position assignation** strings as a secondary “world position” naming family (may be ally companion logic, not Edward).

### Was a position/transform interface discovered?

**No verified callable interface.**  
Exports do not expose pose get/set. Transform string hits are mostly non-player (IK/cloth/render).  
`PlayerPosition` / `player.position` is a **schema name lead**, not a proven memory layout.

### Additional evidence needed

1. Extract the **full contiguous schema/composition document(s)** around `0xA1D77BE` (and siblings) offline.
2. Determine how composition names map to runtime type/component IDs (custom reflection tables).
3. Only after ID/layout is reproducible: design a **read-only** live observer that never invents offsets.
4. Optionally locate shipping PDB (not present beside exe) — do not claim symbols without the file.

### Recommended next technical milestone — **v0.5.3 Schema & Reflection Harvest**

Offline-only:

1. Carve and pretty-print composition/JSON schema regions near `PlayerPosition` / combat `EntityId` fields.
2. Build a catalog of player/actor/spawn/position-related schema keys with file offsets + RVAs.
3. Search for registry/hash tables that index those keys.
4. Produce a shortlist of **candidate observation strategies** for a future read-only telemetry experiment — still no guessed offsets in the ASI.
