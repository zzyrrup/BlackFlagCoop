### High-signal: exact reference to `player.position` schema text

Within / near candidate `0x57AF060`:

```text
RVA 0x57AF8D9  file 0x57AEED9
  48 8D 15 1E F2 A2 04     lea  rdx, [rip+…]   ; -> RVA 0xA1DEAFE = {"name":"player.position",...}
  41 B8 DB 04 00 00        mov  r8d, 0x4DB
  E8 F5 20 BA FF           call 0x53519E0
```

Second site `0x57B032B` also `lea`s the same target with immediate `0x4DB`, then `call 0x1A64E70`.

| Fact | Evidence |
|------|----------|
| Target is the STANDARD event object | ASCII at `0xA1DE0FE` |
| `0x4DB` ≠ single-object size | Object alone is **0x14C** (332) bytes |
| `0x4DB` window content | Starts at `player.position`; spans **5 STANDARD + 1 CUSTOM** event defs |
| Callee `0x53519E0` | Prologue `mov rax,rcx` … `cmp r8, 0xF` — consistent with **pointer+length string/SSO helper**, not a gameplay transform reader |
| Candidate callers | E8 into `0x57AF060` from `0x57A9ED7`; callees include `0x53519E0`, `0x1A64E70` |

**Confidence:** **high** that this code **addresses embedded schema text** for a chunk beginning at `player.position`.  
**Not confirmed:** that it fully parses JSON, builds a registry, or emits live telemetry floats.

## Final answers

1. **Was any code found that references the embedded schema region?**  
   **Yes.** Hundreds of RIP-relative LEAs into the core RVA range; after filtering edge false positives, **exact LEAs to the `player.position` event object** remain.

2. **Was a schema parser or consumer identified?**  
   **Partial.** A **credible consumer site** (`~0x57AF8D9` in candidate `0x57AF060`) references the schema **text chunk**. A dedicated JSON parser / registrar function is **not confirmed**.

3. **Which schema categories does it consume?**  
   The `0x4DB`-byte window starting at `player.position` contains **STANDARD and CUSTOM** event definitions (5+1 in that slice). Not proven to consume the full 23/68 catalogs.

4. **Evidence of runtime descriptor or registry creation?**  
   **Not yet** — only pointer+length into blob → string-like helper.

5. **Can event construction or dispatch be traced?**  
   **No** beyond that helper/follow-on call. LiveTelemetry / Job\*SendEvent have limited code refs to **their strings**, unconnected to this chunk.

6. **Verified connection to `player.position`?**  
   **Yes — to the embedded schema definition bytes.**  
   **No — to live float payloads, Edward, or world transforms.**

7. **Is there a safe path to reading player position / next step?**  
   **Still no supported pose read path.**  
   **Next milestone:** deepen static analysis of `0x57AF060` → `0x53519E0` / `0x1A64E70` (what happens to the constructed string/view; any table inserts), without runtime hooks.
