## Investigation 1 — StringId / attribute binding

### Verified

- `PlayerPosX/Y/Z` remain typed **float** in the `.edata` dictionary (v0.5.5).  
- Those names appear as **JSON-quoted schema tokens** (30 hits each in scanned image; **0** clear standalone C-string copies in sampled hits).  
- Absolute **VA/RVA pointer xrefs** to the dictionary/event string sites were **not found**.  
- Harbour exports related to StringId **do exist**:
  - `Harbour_StringId_Registry_Find` / `Insert` / `LoadFrom` / `DumpTo` / `ClearUnsafe`
  - `Harbour_StringId_GetIdentifierXorValue` / `LeftRotation` / `RightRotation`

### Important executable detail

`GetIdentifierXorValue`, `LeftRotation`, and `RightRotation` share RVA `0x0535F280`.  
Raw bytes there begin with `31 C0 C3` (`xor eax, eax; ret`) — **stubs returning 0** in this build, not a usable hash implementation at that address.

`Harbour_StringId_Registry_Find` at RVA `0x0692E820` **does** look like real code (prologue present).

### Not verified

- Any hash algorithm binding telemetry names to numeric IDs (FNV-1a/CRC32 candidate scans did **not** yield a verified multi-name registry).  
- That Harbour StringId registry stores `PlayerPos*` keys.  
- A name→ID table specifically for telemetry attributes.

**Implication:** attribute binding is likely via **runtime schema-blob parsing** and/or **non-pointer StringId indirection**, not classic relocated C-string pointers.
