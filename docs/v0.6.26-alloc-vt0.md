## Discovered

### Confirmed — Alloc→VT[0] is indirect-only

| Probe | Result |
|-------|--------|
| E8 callers of `0x13612B0` / `0x5781490` | **0** (v0.6.25) |
| Absolute qword embeds of ctor VAs | **Only** at VT bases `0x976B2D0` / `0x9236E00` |
| `movabs` ctor imm64 in code | **0** |
| Allocator E8 + LEA owner VT in same func | **0** (500 Alloc sites sampled; full LEA±0x80 scan **0**) |
| RIP-relative *loads* of VT bases | **0** |
| LEA owner VT sites | Only inside owner ctors / siblings (`0x13612B0`, `0x3D522C0`, `0x5781490`, `0x5563CF0`, `0x6CF34A0`) |

**Confirmed:** VT[0] ctors are **in-place** (`lea vt; mov [rcx],vt; …`). They do **not** call Allocator. Invocation is table/`call [vt+0]` / TypeInfo `[ti+0x50]` style — no static Alloc→E8/abs ctor chain in the PE.

**Hypothesis:** some TypeInfo record’s `+0x50` points at these ctors (or a wrapper that leads to them). Not recovered this milestone.

### Confirmed — SideBlock Alloc + attach on `this+0x98`

| Step | Evidence |
|------|----------|
| Alloc | `0xE95E80` → `call Allocator` with size **0x160** |
| Attach | `mov [rsi+98], rbx` (block pointer on **this**) |
| Back-pointer | `mov [rbx+100], rsi` |
| Sole E8 callers | `0x1AC4DB` / `0x1AC523` inside deferred queue handler **`0x1AC380`** |
| Pre-call | Same loop: `0x725400(r14, dl=1)` then `SideBlock(r14)` |

### Confirmed — Arming/ArmWrap consume the same `+0x98` pointer slot

| Site | Evidence |
|------|----------|
| Arming `0x21085D0` | `cmp qword ptr [rcx+98], 0` then gate stub / `jmp [vt+0x2B0]` edx=2 |
| ArmWrap `0x2108620` | `mov rdi, [rsi+98]` (side-block pointer) |
| Arming E8 | **0** — published at `.edata 0x9490078` (VT-slot) |
| Same-func SideBlock+Arming | **Not found** (Arming not E8-callable) |

**Confirmed (structural / pointer-slot same-instance):** objects that receive SideBlock attach (`[this+0x98] = block`) are the same layout consumers Arming/ArmWrap read when they load `[this+0x98]`. Owner spat/neigh ctors init the same offset (v0.6.25). Queue path `0x1AC380` is the only PE E8 attach site.

**Note:** Spatial `VT[0]` also does `add rcx, 98` (inline subobject). That is a distinct *use* of offset `+0x98` vs SideBlock’s **pointer** store. Arming’s loads treat `+0x98` as a pointer — enrollment-family objects, not the Spatial inline subobject alone.

**Not claimed:** live identity of a specific Neighbor VT instance across SideBlock then Arming (would need live memory or a recovered TypeInfo→VT[0] create edge).
