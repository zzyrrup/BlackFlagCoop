## Executive verdict

Both v0.6.2 leads are **real code**, but neither is what the string names suggest at first glance:

| Lead | RVA | Confirmed role |
|------|-----|----------------|
| Input / `Pad_LockAndTurnMovement` | `0x187F0550` | **37-byte action-bind wrapper** → helper `0x18EADD0` |
| Deferred / `CreateActorsDeferred*` | `0x5CBDFB0` | **Frame-phase registrar** (not the create implementation) |

**No verified edge** connects the input-bind path to deferred actor creation (no shared callees, entity IDs, handles, transforms, or ownership structures recovered).

## Workstream A — Input routing (`0x187F0550`)

### Function boundary (confirmed)

```
0x187F0550  size 0x25 (37 bytes)  ends at RET
56 48 83 EC 20          push rsi; sub rsp,20h
48 89 D6                mov rsi, rdx
4C 8D 05 ..             lea r8, [Pad_LockAndTurnMovement]   ; 0xA10D838
48 89 D1                mov rcx, rdx
BA 01 00 00 00          mov edx, 1
E8 ..                   call 0x18EADD0
48 89 F0                mov rax, rsi
48 83 C4 20 5E C3       epilogue; ret
```

- **Direct `E8` callers to the wrapper:** none recovered.  
- **Absolute qword pointers to entry:** none recovered.  
- Call style is therefore unresolved (vtable / register / tail elsewhere) — **unknown**, not “uncalled.”

### What it actually does (confirmed)

It is **not** a per-frame movement controller. It is a **thin per-action wrapper** that:

1. Takes a caller-supplied object pointer (`rdx`/`rcx`).
2. Passes the ASCII action id `Pad_LockAndTurnMovement` in `r8`.
3. Passes flag `edx = 1`.
4. Delegates to shared helper `0x18EADD0`.
5. Returns the original object pointer.

Sibling wrappers with the same shape:

- `0x187F0A00` → `Pad_Dive`
- `0x1A364370` → `Pad_MayanRotatingLeverTurn` (also calls the same helper)

### Helper `0x18EADD0` (confirmed behavior)

Approximate size ~0xFF (naive `C3` scan is unsafe here: `4C 89 C3` = `mov r11,r8`, not `ret`).

Confirmed steps:

1. Early-out on global at `0xAF6FD48`.
2. Allocates a **0x48-byte** object (`call 0x426EE50`, size `0x48`).
3. Installs vtable **`0x9255320`**.
4. Fills descriptor fields; walks a name table and compares via `call 0x5338010`.
5. Attaches the descriptor through the incoming object.

**Input identifier resolution:** ASCII `Pad_*` / `Key_*` string → table lookup → action descriptor.

**Structures receiving “input” here:** the new 0x48 descriptor + the caller object — **not** a character transform or movement component (none referenced in this path).

### Movement downstream (unknown)

This path ends at **action binding/registration**. No evidence here of:

- applying stick/axis to a transform,
- actor/entity/component handles,
- separate input contexts / local-player indices,
- dispatch to an “active character.”

**Hypothesis (not confirmed):** a later consumer of vtable `0x9255320` / the 0x48 descriptor performs per-frame action evaluation and eventually movement.

**Dispatch model (best supported):** generic action-name system, not a hard-wired player movement controller.

## Workstream B — Deferred creation candidate (`0x5CBDFB0`)

### Function boundary (confirmed)

- Entry `0x5CBDFB0`, end `0x5CBE847`, size **2199** bytes (INT3 run).
- Section: `.impdata`.
- Full prologue (multi-register save + `sub rsp,0xB8`) — real function.
- **Direct `E8` callers / absolute pointers:** none recovered (same caveat as input).

### What it actually creates (confirmed: nothing actor-like)

`0x5CBDFB0` **does not create actors**. It **registers frame phases**:

1. `lea` phase-name strings (`CreateActorsDeferredSingleThreaded`, `UpdateActor*`, `GatherActorComponents*`, …).
2. `lea` handler code addresses.
3. Stores into a coordinator object via tiny setters:
   - `0x4DE3390`: `mov [rcx+0x180], rdx; ret`
   - `0x4DE33A0`: `mov [rcx+0x188], edx; ret`
   - `0x4259C90`: `ret` (nop stub)
   - `0xB61FC0`: `mov rax,[rcx+8]; ret`

### Registered CreateActorsDeferred handler (confirmed edge)

| Phase name | Handler RVA | Prologue |
|------------|-------------|----------|
| `CreateActorsDeferredSingleThreaded` | **`0x1AC380`** | `41 57 41 56 41 55 41 54 56 57 53 48 83 EC 70 …` |

Other registered handlers (sample):

| Phase | Handler |
|-------|---------|
| `GatherActorComponentsForSingleThreadedUpdate` | `0x1A97E0` |
| `UpdateActorControllersSingleThreaded` | `0x7B00B60` |
| `UpdateActorSingleThreaded` | `0x29C6910` |

**Do not infer purpose from the string alone:** the string consumer is the registrar; the create work, if any, lives in **`0x1AC380`** (untraced in this milestone beyond registration).

### Character creation connection

- **To `0x5CBDFB0`:** no — it only wires names/handlers.  
- **To handler `0x1AC380`:** **unknown / next lead** — plausible deferred-create phase body; **not** proven as Edward/character factory, archetype spawn, or transform init.

No entity-ID queue, archetype, or transform-init pattern was confirmed **inside** `0x5CBDFB0`.

## Final report answers

1. **What does the input consumer actually do?**  
   **Confirmed:** 37-byte wrapper that binds/registers `Pad_LockAndTurnMovement` through helper `0x18EADD0` (allocates 0x48 action descriptor, name-table lookup). **Not** a movement controller.

2. **Where do movement commands go?**  
   **Unknown** past action binding. Downstream consumers of descriptor/vtable `0x9255320` are untraced.

3. **What does the deferred creation function actually create?**  
   **Confirmed:** it creates/fills **phase-table entries** (name + handler pointers). It does **not** itself create actors.

4. **Is character creation connected to deferred creation?**  
   **Not via `0x5CBDFB0`.** Possible connection only through registered handler **`0x1AC380`** — **unverified**.

5. **Do the two systems share entity or component references?**  
   **No evidence** of shared references at recovered edges.

6. **Is player ownership separate from actor existence?**  
   **Hypothesis, not confirmed.** Evidence is compatible with separation; no ownership structure was recovered.

7. **What evidence supports two independent Edwards?**  
   **Indirect only:** multi-actor update/deferred phase infrastructure exists. **No** confirmed dual spawn, dual transform ownership, or dual input context.

8. **Next best investigation?**  
   Offline trace **`0x1AC380`** (`CreateActorsDeferredSingleThreaded` handler), then **`0x7B00B60`** / **`0x29C6910`** (controller/actor update), and writers/consumers of action descriptor vtable **`0x9255320`**. Still no spawn.
