## Discovered

### Confirmed — validator expected methods

| VT off | Expected RVA | Role |
|--------|--------------|------|
| `+0x2B0` | **`0x4656C80`** | 10 B trampoline: `mov rax,[rcx]; jmp [rax+0x2B8]` |
| `+0x2B8` | **`0x479E3B0`** | 138 B flag/nested helper (`+0x18→+0xA8`, flags `+0x22/+0x25/+0x26`, may `call [vt+0x2C0]`, continues `0x479E440`) |

Validator also does **`test edx, 0xFFFFFFFD`** (`edx & ~2`): the compare path runs when **only bit1 of edx is set** — i.e. **`edx=2`** matches the arming helper's argument.

### Confirmed — arming-table concrete slots (`0x948FF50`)

| Off | Value | Notes |
|-----|-------|-------|
| `+0x2B0` | **`0x4656C80`** | Matches validator expected trampoline |
| `+0x2B8` | **`0x2108620`** | **Different** from validator's `0x479E3B0` |

**Arming call chain (confirmed):**
```
0x21085D0  (arming helper)
  → [vt+0x2B0] = 0x4656C80   (edx=2)
    → [vt+0x2B8] = 0x2108620
      → call 0x479E3B0
      → then +0x98 side-block work (flags, list helpers 0xC45FB0/0x7250E0/0xB27210)
```

So `edx=2` vcall lands on **`0x2108620`**, which wraps the canonical `0x479E3B0` and adds membership-family `+0x98` processing. Neighbor B's equality check is against the **canonical** pair; arm-table objects use a specialized `+0x2B8`.
